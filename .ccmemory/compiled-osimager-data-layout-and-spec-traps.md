Topic: where osimager's data lives, how it is installed, and spec-authoring traps found along the way.

## Data location: history and current state
- March: ansible venv refactor (2026-03-21 session log, deleted). `venv` replaced by pinned `ansible_version` in specs; data-driven `ansible.json` (per version: python_min/max, pkg name, requirements) read by mkvenv via two-layer resolution (user override possible). Py2 venvs need `pyyaml<5.4` prereq (in requirements) and use `virtualenv`; Py3 uses `venv`. `--skip` skips post-install provisioning; `OSIMAGER_VENV_DIR`/`VENV_DIR` override venv_dir. Rule: new ansible version = a row in ansible.json + `ansible_version` in specs, no engine change. At that time `data/` was removed from the engine into the separate `osimager-data` package.
- June, v1.7.0 to v1.8.0 (2026-06-13 session log, deleted): the data-separation commit landed (osimager_data package, two-layer resolution, XDG paths, constants.py gone). generate.py audit gate: `_classify_sources` now recognizes ignition, archinstall, agama, openbsd install.conf, photon JSON kickstart, alpine answerfile, Proxmox answer.toml, XCP-ng answerfile.xml; `ordered_spec_names()` raised catalog to 20 distros/524 specs. Engine v1.8.0: `run_build_hooks` runs spec-level then platform-level `pre_build`/`post_build`, with pre_build before the build JSON is written so a hook can mutate the ISO (CoreOS/Flatcar Ignition); disk-image import via shared `resolve_url_field` / `resolve_disk_image_url`, `disk_image_url` indexing, `image_import` def. Data-side pieces (coreos_iso_customize.py, disk-import platform JSON, appliance specs) were still pending. openSUSE is not in DIST_INSTALLER (classified per file); FreeBSD/MX/SCO/UnixWare still label `none`.
- v1.9.0 reversal (`baseline-data-lives-in-osimager-data-dir`): the user decided two packages were more pain than one — the separate release cadence that motivated the v1.7.0 split never mattered. Specs, platforms, files, tasks, scripts, ansible.json and examples live in `/src/osimager/osimager/data/` and ship as package data (`pyproject.toml` package-data `data/**/*`, bytecode excluded); `core.py` sets `system_data_dir` to `data/` beside itself; nothing imports `osimager_data`. `/src/osimager-data` and the pip-installed `osimager_data` are dead weight; editing them changes nothing. This supersedes the "data/ removed from engine" statements above and any earlier note claiming the engine is an editable install (wrong).

## Two ways to run
- `bin/mkosimage` (dev wrapper) runs the source tree and sees `/src/osimager/osimager/data` edits immediately.
- `mkosimage` on PATH (`~/.local/bin`) runs a COPIED, non-editable install in `~/.local/lib/python3.12/site-packages/osimager/` (`direct_url.json` has empty `dir_info`). Edits reach it only after `python3 -m pip install --user --break-system-packages --no-deps /src/osimager`. "Install the data package" now means this command.
- Package-data by extension has dropped extensionless/unusual files (alpine `answerfile`, openbsd `install.conf`, `*.ign`). After packaging changes, verify the wheel with a `comm` diff of `find osimager/data -type f` vs `python3 -m zipfile -l`.

## Proxmox VE unattended install (`proxmox-ve-unattended-install-mechanism`)
- Proven end-to-end on stock `proxmox-ve_9.1-1.iso` in qemu/KVM: full unattended install, reboot into installed PVE (`pvetest login:`, web UI :8006). No ISO repack, no `proxmox-auto-install-assistant`, no engine dependency. All verified live via qemu monitor sendkey/screendump.
- Why the old spec never worked: stock ISOs have no answer-file auto-install like kickstart/preseed. The old `boot_command` (`<esc> auto proxmox-start-auto-install<enter>`) was fiction, typed into a GRUB with no such entry/prompt; nothing read `answer.toml`. Auto-install exists only on PVE 8.2+ (3.4-7.4 predate it). The old `answer.toml` was also invalid for 9.x.
- The stock `grub.cfg` already has an `Install Proxmox VE (Automated)` menuentry with kernel arg `proxmox-start-auto-installer`, under Advanced Options, gated `if [ ! -f auto-installer-mode.toml ]`; a prepared ISO drops that toml so it floats to a top-level auto-selected entry. We reach the same boot ourselves.
- Mechanism: `boot_command` edits the always-first default `Graphical` entry (`e`, `<down><down><down><end>`, append ` proxmox-start-auto-installer`, `<leftCtrlOn>x<leftCtrlOff>`). Do not menu-navigate to Advanced Options with down x N: the conditional Serial Console entry shifts positions (editing the default is comport-independent).
- With no `auto-installer-mode.toml` the installer prints "Automatic installation selected but no config for fetching the answer file found!" and drops to a root debug shell (`root@proxmox:/#`) — Proxmox's own documented manual path. Run `proxmox-fetch-answer partition <LABEL> >/run/automatic-installer-answers` (LABEL required; bare `partition` errors "partition label expected"); it mounts `/dev/disk/by-label/<LABEL>` and reads `answer.toml`. Then `exit`: init pipes the answer to `proxmox-auto-installer` (reads answer on STDIN), unattended install, reboot.
- The answer rides on the `proxmox-ais` CD osimager already builds (`cd_files`/`cd_label`); `>>cd_label<<` substitutes into the fetch line.
- answer.toml 9.x schema: kebab-case keys (`root-password`, `disk-list`, not `root_password`/`disk_list`); `country` required; `fqdn` in `[global]` not `[network]`; `from-dhcp` forbids other `[network]` keys; `from-answer` needs cidr/gateway/dns. Conditional `[network]` body emitted via multiline `E>...<E`. Disk device templated via `>>answer_disk<<`.
- Files changed (then in osimager-data; paths now map to `osimager/data/`): `specs/proxmox-ve/spec.json`, `files/proxmox-ve/answer.toml`; at the time both source and the installed copy under `~/.local/lib/python3.12/site-packages/osimager_data/` had to be updated. spec.json: `version_specific` block `[89]\..*` (config: boot_wait 15s + the boot_command); top-level `boot_command` `[]`; new `answer_disk` def (default `vda`), platform_specific `answer_disk=sda` for virtualbox/vmware/vsphere.
- Caveats: `vda` (qemu/virtio) PROVEN; `sda` for vmware/vsphere/virtualbox best-effort, UNTESTED. `<wait60>` (boot to debug shell) tuned for KVM (~35s observed); slower/TCG may need more. Scratchpad harness `sendkeys.py` (qemu HMP monitor keystroke/screendump driver) is reusable for other broken distros (Fedora 43, Debian 13).

## Trap: firmware in spec config (`trap-firmware-in-spec-config-breaks-qemu`)
- Symptom: qemu build halts ~2s after "Starting VM" with only "Qemu failed to start"; `PACKER_LOG=1` shows `-bios efi` and `qemu: could not load PC BIOS 'efi'`. Diagnose with `PACKER_LOG=1 bin/mkosimage ...` and grep `Qemu stderr`.
- Cause: a spec `version_specific` block set `"firmware": "efi"` under `config`. Spec `config` merges straight into the Packer builder, where packer-plugin-qemu's `firmware` is a firmware file path. The osimager selector is the `firmware` def, which drives `firmware_specific` overlays; qemu.json forces `platform_defs.firmware = "bios"` (platform_defs beat spec defs), so on qemu the bios boot_command is used.
- Correct shape (RHEL 8/9/10): `defs.firmware: "efi"`, EFI boot_command + `boot_wait: 45s` in `config`, `firmware_specific` `bios` entry with BIOS boot_command + `boot_wait: 10s`. A `platform_specific` proxmox `config.firmware: ""` override is a tell. Fixed for RHEL 8 in v1.9.0; RHEL 7.* still had `config.firmware: efi` — grep specs for `"firmware"` inside `config` when a qemu build dies at launch.
