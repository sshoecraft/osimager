Assorted group (the clusterer could not fit it to one topic). Common thread: where ISOs come from and how installers fail to boot or find media.

## ISO sourcing

- AlmaLinux keeps ONE point release per major on `repo.almalinux.org/almalinux/<ver>/`. When a new one ships, the old directory is reduced to a `README.txt` ("deprecated ... go to https://vault.almalinux.org/<ver>/") and every pinned ISO URL 404s. The ISOs move to `https://vault.almalinux.org/<ver>/isos/<arch>/AlmaLinux-<ver>-<arch>-dvd.iso` (no `almalinux/` segment). 9.8 and 10.2 shipped the same day (May 2026), retiring 9.7 and 10.1 together. Fix (v1.9.4): in `osimager/data/specs/alma/spec.json` point the retired version at the vault, add the new one on repo, widen `provides.versions`; no rhel spec change needed since alma per-version `iso_url` overrides rhel's `9.*` / `10.*` defaults; generated build for the new version is byte-identical to the old apart from random IDs. Also update hand-written ranges: `README.md` (AlmaLinux row), `docs/reference/spec-reference.md` (alma row), `docs/reference/supported-os.md` (also generated by `docs/generate.py`). Detect: `curl -sSL https://repo.almalinux.org/almalinux/ | grep -o 'href="[0-9][^"]*"'`; `-beta` entries show the next point release. `trap-alma-point-release-moves-to-vault`
- Consequence bug: `OSImager.check_iso_url()` (core.py, called from `run_packer()`) did an unconditional `urllib.request` HEAD on http(s) `iso_url` before every build, so the 404 blocked builds even with the ISO cached in `iso_path` or the packer cache. Symptom: `bin/mkosimage proxmox/pve1/alma-9.7-x86_64 alma-9-1` failed `error: ISO URL returned 404 (not found)` while `mkosimage --list` showed `alma-9.7-x86_64 (*)` (asterisk = iso_local True). `check_iso_local()` (used by `make_index()` for `--list`/`--avail` and `--check-urls` skip logic) already detects a locally cached remote ISO by filename; `check_iso_url()` never consulted it. Fix: call `self.check_iso_local(iso_url)` before the HEAD and return early if true; file:// URLs were already fine (`os.path.exists`). Lesson: any "is this ISO available" check reuses `check_iso_local()` rather than re-deriving cache logic or assuming remote reachability implies buildability. `iso-url-check-ignores-local-cache-bug`
- ISOs live flat in `iso_path` (`/iso`), never in vendor subdirs. Platforms build the path as `>>iso_path<</>>iso_name<<`; spec `file://` URLs must be `file://>>iso_path<</<file>`. Until 1.9.1, 64 spec URLs used `<iso_path>/<Vendor>/<file>` (RedHat/, AlmaLinux/, Debian/, SUSE/, Windows/...); `check_iso_local` and pre-flight `check_iso_url` test the literal file:// path, so those targets vanished from `--list --local --avail` and failed "ISO file not found" even with the ISO at the root. User corrected directly: "I thought everything just went into /iso".
  - `/iso` is a symlink to `/data/media/cdimages/os/` (NFS, 11T, ~91% full). `ls -F /iso` / `find /iso ...` without trailing slash or `-H` report the LINK (this produced a false "no subdirectories" claim): use `/iso/` or `readlink -f /iso`. `find -type f` skips symlinks, which hid most of `template/iso/`.
  - `template/iso/` is a Proxmox directory-storage ISO store - never clean it up. PVE host mounts the share at `/mnt/pve/iso` (absent on this box); Proxmox lists ISOs only under `<storage>/template/iso/`, so ~151 entries are symlinks `-> /mnt/pve/iso/<file>` (dangling from here, valid on PVE). ~11 regular files (AlmaLinux, debian, `packer*.iso` cd_files CDs) are uploads from Proxmox / osimager proxmox builds and may be attached to PVE VMs. A killed cleanup nearly deleted them as "duplicates/leftovers".
  - The share is also a vSphere datastore: `vCLS-*` dirs (live vSphere Cluster Services VM disks) and `.vSphere-HA` - never touch. `os -> .` and `packer_cache -> .` are self-referencing symlinks - don't recurse with `-L`.
  - Leftover vendor subdirs (`RedHat/`, `AlmaLinux/`, `Debian/`, `Windows/`) hold non-ISO helpers (`d`, `dl`, `t`, `tl` scripts, Windows serial/license text) - leave them. Duplicate ISOs outside `template/iso/` are removed only after byte-for-byte `cmp` against the root copy and with user go-ahead. `iso-path-is-flat-and-a-symlink`

## Installer failure modes

- qemu build VM with no `-cpu` gets `qemu64` (baseline x86-64; packer-plugin-qemu passes no `-cpu` unless `cpu_model` is set). RHEL 9 glibc needs x86-64-v2, RHEL 10 v3. Symptom: build hangs forever at "Waiting for the guest address... br0"; console shows `Attempted to kill init! exitcode=0x00007f00` (init exits 127) ~26s into boot; build disk stays ~196 KB. RHEL 8 fine on the same host. Fix (1.9.1) in data, not core.py (whose bridged-NIC `qemuargs` block also never had `-cpu`): `platforms/qemu.json` config `"cpu_model": "E>'host' if os.access('/dev/kvm', os.W_OK) else 'max'<E"`, mirroring the `accelerator` expression; `-cpu host` refuses to start under TCG, hence `max`. Covers bridged and non-bridged. Finished VM unaffected: `scripts/qemu_post_build.py` writes libvirt XML `<cpu mode='host-passthrough'/>`. Verify: `PACKER_LOG=1`, grep the `Executing /usr/bin/qemu-system-x86_64` line for `"-cpu", "host"`; healthy install reaches "Found guest address" and disk grows past hundreds of MB within minutes. `trap-qemu64-cpu-panics-rhel9-installer`
- Debian d-i seed CD (debian.seed / debian_12.seed / debian_pre10.seed + debian.fix), verified against Debian 13.1 installer (apt-setup 0.198, base-installer 1.226):
  - file-preseed.postinst runs `preseed preseed/file` then `preseed_command preseed/early_command` back to back. Seed comes from /media, mounted by a timed boot_command keystroke after ~50s that can lose the race on a slow host. So `early_command` must mount the `cd_label` CD itself by label (blkid | grep LABEL=). Never `|| true` the copy: a silent miss surfaces later as "apt configuration problem" or a DVD prompt and the build sits there (25-minute "slow" parallel builds were both parked at that dialog).
  - base-installer library.sh `configure_apt()`: bind-mounts /cdrom -> /target/media/cdrom, writes /target/etc/apt/apt.conf.d/00CDMountPoint and 00NoMountCDROM (NoMount, AutoDetect false), runs apt-cdrom add.
  - Stock generators/40cdrom on a real CD drive REMOVES 00NoMountCDROM, unmounts /target/media/cdrom* and /cdrom, then lets apt-cdrom find a drive itself - fails with the seed CD as second drive (sr1).
  - debian.fix installs as post-base-installer.d/10debian-fix and replaces 40cdrom; the replacement must rebuild configure_apt's state (bind + both conf files), not just sed sources.list, or pkgsel/tasksel asks for the DVD.
  - finish-install 90base-installer removes 00NoMountCDROM at the end; 10apt-cdrom-setup keeps cdrom entries for a real CD.
  - Read real scripts: extract /install.amd/initrd.gz from the DVD ISO (`xorriso -osirrox on -extract`), and pool/main/a/apt-setup/*.udeb, pool/main/b/base-installer/*.udeb (`dpkg-deb -x`). `trap-debian-installer-seed-cd-and-40cdrom`

## Early-2026 session findings (2026-03-12)

- Proxmox: patched `packer-plugin-proxmox` v1.2.3 (PR #283 merged); `skip_convert_to_template` defaults true, don't set it; `post_build` re-enabled and `proxmox_post_build.py` only renames the VM.
- VMware Workstation: ESXi VM lost network because the VMX lacked `ethernet0.connectionType`/`vnet`; ESXi firewall DROP also blocked; ESXi needs minutes to initialise. NFS export for the `vms` datastore; `esx.json` location targets the ESXi host.
- FreeBSD: boot command `cd2 || cd1 || cd0` for vSphere; installerconfig installs sudo, python3 and conditionally open-vm-tools during OS install, since base lacks pkg/python/sudo.
- Kickstart: `--hostname` was inside the static-IP conditional so DHCP builds got `localhost`; fixed in kickstart_5..9 (3 and 4 were fine).
- Alma 9 on nested ESXi: soft-lockup warnings are expected; `nmi_watchdog=0` suppresses them.
- Open at the time: qemu alma-9.7 console kernel crash (later explained by the qemu64 CPU trap above), spec merging bug (top-level arch_specific overrides version_specific), mystery `~steve` dir on built VMs, pve `vm_storage_pool` should be "vms".
